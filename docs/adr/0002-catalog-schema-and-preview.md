# ADR 0002: Catalog foundation and API-backed preview

Date: 2026-10-24. Status: accepted.

The catalog starts as one NestJS module owning games, versions, characters, aliases, stats and skills. It exports a public read service and an internal writer interface. No HTTP mutation controller is available before identity/RBAC in Phase 3. The writer validates versioned mechanics and performs parent/child replacement in a transaction.

Use TypeORM EntitySchema mappings with explicit migrations and named constraints. UUIDs are generated by Node's `randomUUID()` rather than requiring a database extension. Random UUID index locality is an accepted trade-off for this small initial catalog; revisit UUIDv7 if measured scale warrants it. Use relational columns for filters and relationships. Mechanics v1 contains only optional `attackType` (Melee/Ranged); unknown keys and versions are rejected by the writer.

Game patch releases are separate records. No release is seeded without a verified patch identifier/date. Public reads require an active game and published catalog record. RLS is enabled without public policies on all catalog/foundation tables: NestJS serves the public API through the trusted database connection; Supabase Data API roles must not read drafts. A future least-privilege API database role needs an explicit RLS policy/privilege design; the current local setup uses the user's configured postgres connection.

Seed only six reviewed records. Keep missing stats, skills and voice credits empty/null rather than importing unverified values. Store source URL and verification date; asset paths preserve the export without claiming new redistribution permission. Seeding inserts missing records and never overwrites editorial changes.

Keep `demo-ui/` unchanged. `apps/web/server.py` renders the character directory/details from the REST API at request time, reusing demo CSS, artwork and JavaScript. It returns an unavailable page on API failure instead of silently using mock catalog JSON. Pagination is fully traversed for the small catalog so client filters/search see every published record. This is a local integration preview, not the final production web server. Other demo pages remain static until their roadmap phases. Preserve saved names even when the API catalog covers only part of the original roster.
